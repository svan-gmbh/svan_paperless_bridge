# AGENTS.md - svan_paperless_bridge

Frappe app (v16, Python >= 3.14, Paperless NGX >= 3.0; built for ERPNext but without `required_apps`, `svan_base` optional, see "Navigation and SVAN logo") that bridges Frappe's core `File` DocType and Paperless NGX. Attachments of whitelisted DocTypes are uploaded by scheduled jobs, their metadata comes from the business document they are attached to, and changes made later on either side are kept in sync. Module name: "SVAN Paperless NGX Bridge"; DocTypes live in `svan_paperless_bridge/svan_paperless_ngx_bridge/doctype/`.

This file describes the current state of the code. Rewrite the affected passage when something changes; do not append history.

## Commands

- Install/state: `bench --site <site> install-app svan_paperless_bridge`; `after_install` creates the custom fields, fills the file type whitelist and places the desktop icon; `after_migrate` recreates and places the desktop icon, see "Navigation and SVAN logo". New installs mark all patches as done; `after_install` already creates the current state.
- Changed custom field definitions reach existing sites only through a patch that calls `custom_fields.create_svan_paperless_custom_fields` (see `patches/add_svan_paperless_version_id_to_file.py`); without one run it via `bench --site <site> execute`.
- Changed `scheduler_events` in `hooks.py` only take effect after `bench migrate`.
- Maintenance (testing/debugging), all via `bench --site <site> execute svan_paperless_bridge.utils.maintenance.<fn>`: `reset_sync_state` (clears sync log, import queue and scan watermark, tag/correspondent mappings, file sync state; keeps config), `restore_physical_files_from_paperless` (run it BEFORE `reset_sync_state` to cover offloaded files), `reset_settings_to_fresh_install` (then `bench clear-cache`).
- Lint/format: `ruff` (tabs, line length 110, py314), eslint, prettier via `.pre-commit-config.yaml` (Frappe app template standard). The hook runs on every commit; set it up once per clone with `uv tool install pre-commit && pre-commit install`, run everything manually with `pre-commit run --all-files`. A reformatting shifts the line numbers in the `locale/*.po` comments - regenerate the catalog afterwards.
- Tests: `bench --site <site> run-tests --app svan_paperless_bridge` against a REAL Paperless NGX; no mocks of the API. Use a dedicated site (only frappe + svan_base + this app; `test_navigation` also runs on a site without svan_base and checks the standalone case there) with `allow_tests` and `svan_paperless_test_api_url`/`svan_paperless_test_api_token` (superuser token) in its `site_config.json`; without them the tests are skipped. A full run takes about 15 minutes (the upload waits for Paperless NGX to consume each file). `PaperlessTestCase` (`tests/paperless_test_case.py`) configures the Settings, patches `frappe.db.commit` to a no-op (the app commits per file) and rolls back after every test, then clears the Settings document cache and the watched DocType map (Redis is not rolled back). The commit patch stays active during that rollback, and a second rollback discards what `after_rollback` callbacks wrote. Every name that reaches Paperless NGX (party titles, tags, custom fields, default correspondent, document type, file names) carries a per-test prefix `svantest-<hash>`; `tests/live_paperless.py` deletes exactly that afterwards (documents including the trash, entities, users), and `setUpClass` removes leftovers of aborted runs. "Unreachable" is a dead URL (`127.0.0.1:9`). Business documents are the custom DocTypes `Svan Test Party`/`Svan Test Invoice`, created once per site (DDL commits implicitly, so they stay). The base Settings whitelist the invoice; `ReferenceTestCase` (`tests/reference_test_case.py`) adds a reference on the invoice ID and documents created directly in Paperless. A PNG for Paperless must be OCR-able (a tiny one fails the consume task with `SubprocessOutputError`). Test PDFs come from `make_pdf()` because Frappe parses PDFs on insert. Desk behaviour (dialogs, duplicates section, download guard, chunked upload) was checked once with a headless browser, it is not part of the suite. Not testable live and therefore not covered: failed or duplicate-rejected upload tasks (Paperless NGX rejects unreadable content already at upload), a document list that ignores the `id__in` filter (the guard in `paperless_compare`). Also not covered yet: amend copies, runtime/file limits, maintenance scripts, the client-side confirmation dialogs (deleting an original with versions, reference change on save; `check_reference_change` behind the latter is covered).
- `README.md` (English) and `README.de.md` (German, "du") are the user-facing introduction for customers and consultants: what the app does, requirements, install (from the release branches `version-16`/`staging-16`) and configuration, where to find things in the UI (per navigation mode), collapsible tables of the Settings buttons and of when each change is transferred (at once vs. next run), update/uninstall steps. Any DocType takes part, so they say "record"/"Datensatz", not "business document"/"Beleg". UI names in the German file are the `de.po` translations. Keep both in step when UI locations, buttons, timing or update steps change. Internals belong here, not there; nothing about the development environment, development branches or issues.
- i18n: all source strings are English. German term for "custom field" (Paperless and Frappe) is "Zusatzfeld"; DocType names and technical identifiers stay English. `_()` in Python, `__()` in JS, German in `locale/de.po`. A `__()` nested inside another `__()` is not extracted (assign it to a variable first). Custom field labels/descriptions in `custom_fields.py` are extracted by `gettext_extractors/custom_field_definitions.py`, registered in `babel_extractors.csv`. ## Data model

DocTypes (all System Manager only; names `SVAN Paperless ...`):

- **Settings** (single): `api_url`, `api_token` (Password), `default_correspondent` + resolved `svan_default_correspondent_id`, `whitelisted_doctypes` (child), `whitelisted_file_types` (child, MultiSelect), `sync_config_version`, `delete_physical_file` (label "Keep File Content Only In Paperless NGX", default on; also decides whether an import downloads the content), `archive_deleted_files` (label "Archive Instead Of Deleting", default on; a patch sets it on existing sites; a msgid "Archive" would share Frappe's own translation "Archivieren"), `enforce_document_permissions` (default on), `webhook_secret`, file import: `import_reference_mapping` (Link to a Custom Field Mapping; enables the import), `import_tag` (Link to Tag, needs the reference), `max_import_attempts` (10; a patch sets it on existing sites, singles get no defaults for added fields), hidden `import_scan_watermark`, and three hidden tuning fields: `api_call_timeout` (30), `max_runtime_seconds` (240), `max_files_per_run` (100; `0` pauses uploads while classification still runs).
- **Whitelisted DocType** (child): `document_type`, `paperless_document_type_name` (defaults to the translated DocType name), resolved `paperless_document_type_id`, `party_fieldname` (Link field, or a Dynamic Link such as `Quotation.party_name` whose type field `quotation_to` must be a Link to DocType or a Select), `party_rename_supported` (computed, always 0 for a Dynamic Link). Each DocType may appear once. The document type mapping lives here; there is no separate mapping DocType for it.
- **File Type** (named by upper-case extension without dot, matching Frappe's `File.file_type`) + child **Whitelisted File Type**.
- **Tag Mapping** (`frappe_tag` <-> `paperless_tag_id`, `bidirectional` (default 1, no Settings default), `last_synced`), **Correspondent Mapping** (`frappe_party_type/frappe_party` <-> `paperless_correspondent_id`, `bidirectional` (default 1, no Settings default), `last_synced`), both created automatically. **Custom Field Mapping** (name, type, `bidirectional` (default 1, no Settings default), child **Custom Field Source** = `source_doctype`/`source_fieldname`) is user-maintained configuration (links show the Paperless name, the record name is a hash); `File` is rejected as a source DocType, the ID `name` is allowed as source field (offered as "ID (name)"). One Paperless custom field may be fed from several DocTypes (e.g. one "Customer name" for all sales document types), but each DocType only once per mapping.
- **Import** (named by `paperless_document_id`): `status` (`pending`/`imported`/`not_found`/`ambiguous`/`failed`), `attempts`, `last_attempt`, `business_doctype`/`business_name`, `file`, `details`. Internal work table of the import (no workspace/sidebar link); read/delete only. Like the sync log in `ignore_links_on_delete`.
- **Sync Log**: `log_datetime`, `log_type` (Info/Warn/Error), `source`, `reference_file`, `title`, `details`, `context` (JSON). Read/delete only. `context` holds the settings stamp and, with a file, the File row (without content, `owner`, `modified_by`) and its business document's tags, party, mapped custom field values and whitelist row, each with the mapping row of that moment; a failed snapshot stores `collect_error` instead and never blocks the entry. "Export as JSON" in the list's actions menu (`export_sync_logs`): selected entries only; no import. Frappe's Log Settings delete entries after 90 days by default (`clear_old_logs`).

Custom fields (module "SVAN Paperless NGX Bridge": the marker tooltip names the app through it, and uninstalling the app deletes them) on `File` (all `svan_` prefixed, read-only/hidden except status): `svan_paperless_document_id` (indexed; always filter it with a string - compared with a number, MariaDB converts every row and skips the index), `svan_paperless_version_id` (the version holding the file's content; equals the document ID for the original, empty while an upload task is open), `svan_paperless_uuid` (upload task UUID), `svan_paperless_sync_status`, `svan_paperless_config_version_checked`, `svan_source`, `svan_paperless_needs_update`, `svan_paperless_synced_name`/`_synced_title`/`_synced_label` (see "File names"). On `User`: `svan_paperless_api_token` (personal token, Password, no permlevel).

Sync status values: `""` (not relevant) -> `pending` -> `syncing` -> `synced`; terminal: `broken`, `deleted`. Neither `broken` nor `deleted` is ever reclassified automatically, but a `broken` file whose document or version is gone is deleted like a `synced` one (see "Comparison with Paperless") (button "Reset Broken" clears status, UUID, document and version ID and the config stamp of all `broken` files).

`broken` is reserved for KNOWN unsolvable causes (unsupported file type, duplicate rejection, defective image, content only in Paperless but the document is gone: preview/push 404, amend copy without original). Unknown failures stay `pending` and are retried every run with a Warn entry in the sync log - decided deliberately: Paperless NGX reports task errors only as free text, so a Tika/Gotenberg/OCR problem fixed later must not leave files stuck.

Navigation and SVAN logo. `svan_base` is optional (no `required_apps`, Frappe Marketplace): installed, the app joins its "SVAN" entry; without it, the app stands on its own. Frappe has replaced the navigation mechanism within v16 more than once (apps screen entry, then desktop icon below "SVAN", then from 16.50 dock/rail and sidebar header); each time the logo vanished because it hung on one-off data. Everything is therefore declared in files and hooks rather than records, and every decision lives in `navigation.py`:
- Logo: own copy `public/images/svan-logo-icon.svg` (same file as svan_base's), declared as `app_logo_url` and in `add_to_apps_screen`. With svan_base the rail shows svan_base's logo and the desktop icon uses svan_base's file.
- Apps mode (Frappe >= 16.50): the dock `dock/svan_paperless_bridge/svan_paperless_bridge.json` has `mount_on: "svan_base"`. Frappe only honours a mount whose host is installed and ships a dock; then the entry "Paperless NGX" sits on the SVAN rail after "SVAN Base", the rail shows svan_base's logo, the sidebar header the module icon (`archive`), and the mount keeps the app off the apps screen. Without svan_base the mount is ignored and `add_to_apps_screen` gives the app its own slot with its own rail (same dock entry) and logo.
- `add_to_apps_screen.has_permission` = `navigation.show_own_app_entry`: True only standalone in Apps mode. It hides the own entry on the pre-16.50 apps screen and the own "App" desktop icon, which the Desktop Icons grid never shows.
- Desktop Icons grid (mode "Desktop Icons", kept by sites upgraded to 16.5x): all SVAN apps share one main entry "SVAN" - svan_base's App icon, or without it a Folder "SVAN" (same label and logo) created by the first SVAN app that brings more than one icon; a folder never holds a single icon (dissolved, the icon goes to top level). This app brings one icon, so alone "Paperless NGX" sits at top level, otherwise below "SVAN", with svan_base's or its own logo. Each SVAN app runs the same check (`navigation.create_desktop_icon`: Frappe's idempotent seeding, main entry if needed, placement, dissolve) after every migrate and on `after_app_install`/`after_app_uninstall` of any app. Frappe deletes an uninstalled app's App icon together with every icon below it, and creates no App icon while any icon is named like it. svan_base therefore moves the icons below "SVAN" to top level before its own uninstall and replaces a Folder "SVAN" by its App icon on install (its `navigation.py`); this app's `before_app_install` removes the folder from this side as well, for svan_base versions without that (otherwise svan_base's `before_install` ran first and it finds none). `after_app_uninstall` re-places the own icon and switches to the own logo. `before_uninstall` removes the own icon and dissolves the folder if needed. `set_value` bypasses `Desktop Icon.on_update`, so the cached grids are dropped explicitly. Svan_base never knows any of this; other SVAN apps that become optional need the same module.

Do not "correct" them. Standalone behaviour was verified on 16.52 only.

## Flows

**Whitelist.** Every sync step only handles files whose `attached_to_doctype` is whitelisted (`utils/whitelist.py`): upload and classification, poll, metadata push (flags of other DocTypes wait), webhook (a document whose files all belong to other DocTypes is ignored, not imported), comparison, version import, name sync, relink (`ImportRules.covers`), deletion in Paperless, offloading, and the reconcile clears of tags and custom field values. The preview is no sync and keeps serving offloaded files. Removing a DocType leaves its files as they are on both sides; adding one (again) flags its synced files for a metadata push (`flag_files_of_added_doctypes`, ERPNext wins).

**Classification.** `reconcile_file_classification` re-evaluates only files whose `svan_paperless_config_version_checked` differs from `Settings.sync_config_version` (bumped when the DocType or file type SET changes, and manually by code that saves settings with `ignore_validate`). A file is relevant if it is not a folder, not on Dropbox/Google Drive, its `attached_to_doctype` is whitelisted AND (its `file_type` is whitelisted OR the MIME type guessed from the name is). Empty whitelists mean "nothing allowed".

**Upload.** `sync_pending_files` (cron, 5 min) validates settings, classifies, then per file calls `query_uuid`. While a reference for the import is set, a file of a whitelisted DocType the reference has no source on (a gap, `reference_config.has_reference_gap`) stays `pending` and every attempt logs a Warn - its document would carry no reference and be detached on its next change. Otherwise: atomic `pending -> syncing` reservation (raw UPDATE + commit), SHA-256 checksum lookup in Paperless that adopts only a document no other File owns (an orphan, e.g. from an upload whose UUID was never saved) and that no open upload task of another file with the same `content_hash` created (such a file only knows its task UUID until its poll; the tasks are queried, a failed check means no adoption): `_adopt_existing_document` first overwrites its metadata with the state of the business document (`_patch_document_metadata`), then sets `svan_paperless_document_id` (the poll job finishes it; the title is left as found); a failed push puts the file back to `pending`, HTTP 404 falls through to a normal upload. Otherwise multipart `POST /documents/post_document/` with title, created, correspondent, tags, document_type, custom_fields (JSON string `{id: value}`). `None` values must be omitted (multipart would send the string "None"). The returned task UUID is stored by `save_uuid` (5 attempts; after that status `broken` but the UUID is kept so no duplicate is uploaded). On HTTP 400 with an invalid tag/correspondent/document type/custom field ID the matching `repair_stale_*` runs and the upload is retried once (`MAX_UPLOAD_REPAIR_ATTEMPTS = 2`). A 400 "File type X not supported" marks the file `broken` and removes that extension from the whitelist; a request exception, invalid JSON or any other non-200 status (including an unknown 400) puts it back to `pending` for the next run. A copied attachment from an amended document whose `file_url` is already the preview route (`amend_copy.prepare_amend_copy_for_upload`) gets the original's current content restored from Paperless and its sync fields reset (status `pending` like any new eligible file, UUID and document ID empty, config version stamp `0` so the whitelists are re-checked before the upload, needs-update flag off), so it is uploaded as a document of its own; without a synced original (or on 404) it becomes `broken`, on a transient error it returns to `pending`. `file_events.sync_immediately` makes an optimistic first attempt on insert (5 s timeout, never `broken`, falls back to `pending`).

**Versions.** `file_versions.find_version_target` runs first in `query_uuid`. The group of a file are the other files of the same business document whose name is equal after removing an optional 6-hex suffix before the extension (Frappe appends `content_hash[-6:]`, random on a collision, whenever the path exists on disk - site-wide, so the original may carry one and a later file may lack one once the original was offloaded). Any `synced` group file supplies the document (the most recent one if several exist from before versioning): the file is sent as `POST /documents/<id>/update_version/` (label = file name, no metadata), the document ID is stored at once and the poll adds the version ID from the task. Without a synced one, the earliest queued (`pending`/`syncing`) group file uploads normally and later ones stay `pending` silently; a `broken`/`deleted`/irrelevant group file does not block. A 404 on `update_version` (document gone) falls through to a normal upload. Before the upload, a version of the document with the same SHA-256 (`versions[].checksum`) that no File holds (e.g. added in Paperless and not imported yet) is taken instead: document and version ID are stored, the poll completes the file. Otherwise same content still becomes a version. A file without version group looks the same way through the documents of all other files of its business document (`_take_unclaimed_version`, never another business document's: its metadata would be wrong), so content attached again takes back its archived version; `align_uploaded_file` then names it, which drops the mark. Files synced as documents of their own before versioning stay as they are.

**Finalize.** `poll_syncing_files` (cron) asks `GET /tasks/?task_id=<uuid>` while the version ID is empty (`_store_task_result`): `success` -> `related_document_ids[0]`, stored as document and version ID for a new document, as version ID only when the document ID was set by a version upload; a failed task or a success without document ID goes back to `pending` without UUID (`_queue_for_new_upload`, retried every run; the failed task created no document), only `duplicate_of` (`PAPERLESS_CONSUMER_DELETE_DUPLICATES=true`, which must be off) and `UNSOLVABLE_TASK_ERROR_RE` (unsupported mime type, defective image conversion) mark the file `broken`. A document ID another File already owns is never taken over: the file clears its UUID and goes back to `pending` for an upload of its own (`_requeue_for_own_document`). After a `_document_still_exists` check (a missing document or version means a new upload), `finalize_sync` sets `synced`; with `delete_physical_file` it first removes the content on disk and sets `file_url` to the preview route (`/api/method/svan_paperless_bridge.preview.stream/<name>?file_name=<File name>`). The route prefix is duplicated in `preview.PREVIEW_METHOD_PATH` and `public/js/file.js`; keep them equal. `retroactively_delete_physical_files` applies the same to already synced files.

**Preview.** `preview.stream` checks Frappe read permission, then (private files + `enforce_document_permissions`) `document_access.has_paperless_document_access` using the user's own token (HTTP 200 on `GET /documents/<id>/` = access, fail-closed), then downloads with the service token, always with `?version=<own version>` (without it Paperless serves the newest version; `&original=true` for natively previewable types). A 404 marks the file `broken`. `restore_physical_file_from_paperless` downloads the own version the same way.

**Forward metadata updates.** `change_watch` keeps a cached map of watched DocTypes (whitelisted DocTypes + their party field and, for a Dynamic Link, its type field, mapped custom field source fields, party target DocTypes' title fields). The possible targets of a Dynamic Link are the Select options of its type field, or, for a Link to DocType (open set), the party types present in Correspondent Mappings. The wildcard `on_change` hook returns after one dict lookup for unwatched DocTypes. On a relevant change it flags all `syncing` and `synced` files of that business document (`svan_paperless_needs_update = 1`, raw UPDATE + commit); `syncing` is included because its upload is already sent, the flag waits for `finalize_sync`. `sync_metadata_updates` (cron) then calls `push_metadata_update` once per document (versions share business document and metadata; the other files' flags are just cleared): fresh `PATCH /documents/<id>/` (JSON via `frappe.as_json`) with tags, correspondent, document type and custom fields. Paperless replaces the whole `custom_fields` list, so the document's current entries are loaded first and entries not owned by a mapping are preserved; owned IDs without a current value are dropped, which clears them in Paperless. Correspondent: if the DocType has a `party_fieldname` but it is empty, the correspondent is cleared; with no `party_fieldname` the default correspondent applies. Renaming a Frappe tag or a party title field additionally PATCHes the existing Paperless tag/correspondent. Renaming a watched business document (wildcard `after_rename`; Frappe has already moved the attachments) flags its files, so an ID-based custom field such as the reference gets the new name. `push_metadata_update(..., previous_doctype)` also clears custom fields only the previous DocType of a moved file had a source for. The cache is invalidated by Settings and Custom Field Mapping `on_update/on_trash` and by a Correspondent Mapping whose party type is new or changed. Metadata directly on the `File` document is not synced, except its name (see "File names").

**Reverse sync.** `webhook_sync.receive_update` (allow_guest, secret in header `Webhook-Secret`, compared with `hmac.compare_digest`, fail-closed; then elevates to Administrator) takes `document_id`, finds all Files with that ID (none: hands it to the import, no log entry), loads the document once (a 404 ends the call), deletes the files of deleted versions (see "Comparison with Paperless"), lets `paperless_import.relink_linked_document` move or detach them, imports new versions and takes over changed file names (after the relink, so they join the files at their new business document; then nothing is applied back if the files moved), deduplicates to business documents (a file deleted meanwhile, e.g. archived by a deletion whose mark fired another webhook, is skipped), skips (Info entry) a business document whose file has a pending metadata update (ERPNext wins; Paperless still shows the old state, e.g. no correspondent and the import tag after a failed push right after an import, which would clear a mandatory party) and applies, per business document: tags (each tag of the Paperless document gets a mapping row if missing; add and remove only for mapped `bidirectional` rows, unmapped Frappe-side tags are never removed), party relink (per Correspondent Mapping `bidirectional`: `correspondent_sync.ensure_party_for_paperless_correspondent` looks up the row by Paperless ID or, if missing, finds the party by exact title match and creates the row - race handled like tags; 0 matches / correspondent removed clear the link only if the current party's row is bidirectional, >1 matches skip; a Dynamic Link only relinks to a party that already has a row of the document's current party type, the type field is never changed), custom field values (mapping `bidirectional`, non-Link targets only, missing value clears). Every field is saved separately with `doc.save`, 5 attempts, failures only logged. The document type is never synced back. `frappe.flags.svan_paperless_applying_webhook_update` suppresses `change_watch` flagging while Paperless changes are applied (prevents ping-pong).

**Import.** `paperless_import`: a Paperless document qualifies when its document type is the one of a whitelisted DocType the reference mapping (`Settings.import_reference_mapping`) has a source on, the reference custom field has a value and, with `import_tag`, it carries that tag, and while the archive is on its title carries no archive mark (`paperless_import._qualifies`; `import_rules.ImportRules`, one rule per such DocType, resolving document type/custom field/tag IDs like on upload). Sources: `receive_update` for a document without File (`import_unlinked_document`, processed at once) and `import_from_paperless` (daily safety net, button "Import From Paperless NGX Now"), which scans ALL documents changed since `import_scan_watermark` (`GET /documents/` with `ordering=modified`, `fields=` (otherwise the full OCR text comes along), `modified__gt`; the highest `modified` seen is stored after every page without touching the Settings' `modified` - the clocks of Frappe and Paperless never meet; empty watermark = full scan), hands linked ones to the relink, queues qualifying unlinked ones, then works through `pending` rows. `process_import` locks the row (`for_update`), so webhook and cron never import twice. Reference value stripped of surrounding whitespace/line breaks (blank = no reference; MariaDB ignores trailing spaces, so `'   '` would equal every empty field) and searched with `frappe.get_all(doctype, {source_fieldname: value})` over all matching rows, case-insensitive through the collation: 0 -> retry every run up to `max_import_attempts`, then `not_found`; >1 -> `ambiguous`; an exception -> retry, then `failed`. A later change in Paperless (webhook or scan) restarts `not_found`/`failed` rows; `ambiguous` only the button "Reset Import Queue". A document that no longer qualifies drops its row, a 404 too. Import: download the NEWEST version not archived (`?version=`; the original is the oldest), insert a private File (`create_version_file`, shared with the version import) named after that version: its label if set (with the extension of the uploaded name, `name_sync.file_name_from`), otherwise the name it was uploaded with (`GET /documents/<id>/metadata/?version=<vid>` -> `original_filename`; the download header only names the document); a suffix Frappe adds for a name existing on disk stays in the path only (`file_name` is set back after the insert); with document = root ID, version = that version, `svan_source = paperless`, then `finalize_sync` (offloads per `delete_physical_file`); Paperless tags are added to the business document except the import tag, then the metadata are pushed at once (Frappe wins: tags without the import tag, correspondent, custom fields; on failure the flag is left for the regular push) - a pending update would keep the file from following a change in Paperless. `file_events.sync_immediately` skips files that already have a document ID. The reference mapping is never applied back from Paperless: saving the Settings or the mapping switches its `bidirectional` off with an alert (`is_import_reference`), the form locks the checkbox; webhook and reconcile skip non-bidirectional mappings anyway, and `name` is no field they could write.

**Relink.** While a reference is set, `document_relink.relink_document` makes linked files follow their Paperless document (webhook and import scan, all files, also those uploaded from ERPNext). Skipped: a file not `synced` or with a pending metadata update (ERPNext's update wins, e.g. the backfill), files of a document spread over several business documents (legacy), and files of a DocType without reference source (a gap DocType is never touched). Document type + reference (import tag NOT needed) match exactly one other business document -> all files (versions) are attached there (attachment comments on both timelines) and its metadata pushed at once, without leftovers of the previous one; no match, several matches, empty reference or a document type without rule -> the files are deleted in ERPNext inside `paperless_delete.keeping_paperless_documents()` (the document stays with its old metadata) and the queue row is dropped, so a later valid reference imports it again (with the import tag if configured). Each move/detach is logged (Info) with the reason.

**Reference configuration.** `reference_config`: setting/switching the reference (Settings `on_update`) or changing the sources of the reference mapping (mapping `on_update`; a rename of the custom field alone only renames it in Paperless) flags all `synced` files of DocTypes with a source for a metadata update (backfill), so Paperless gets the new reference values before anything is moved or detached. Both forms call `check_reference_change` in `before_save` (`reference_change_confirm.js`): a dialog lists gaps and the number of files to backfill; closing it cancels the save, "Save Anyway" saves. Clearing the reference stops import and relink. Every change of what qualifies for the import (reference, its sources, import tag, whitelisted DocTypes and their document type names) empties `import_scan_watermark`, so the next scan looks at all documents again; otherwise documents scanned under the old rules (e.g. without the then required import tag) would never be imported.

**Comparison with Paperless.** Paperless NGX has no trigger for deleting a document or restoring a document or version from the trash (checked up to 3.3.4; the feature request was declined), so `compare_with_paperless` (cron, 5 min) lists the documents of all `synced`/`broken` files of whitelisted DocTypes with a document ID in batches of 100 (`GET /documents/?id__in=...&fields=id,title,versions,original_file_name`). A batch whose answer fails or lists other IDs than requested deletes nothing. A missing document (the trash counts as deleted) deletes all those files and drops its import queue row (so a document restored from the trash, which bumps `modified` but fires no webhook, is imported again by the next scan - with an import tag configured only once the tag is set again, since the import removed it; setting it fires the webhook, which imports at once; Paperless exposes the restore only in `/documents/<id>/history/` (`restored_at`), not as a field or filter); a missing version deletes only the file holding it. Deleting a version fires "Document Updated", so `receive_update` calls `delete_files_of_deleted_versions` at once. Deletion runs inside `keeping_paperless_documents()`: Paperless is not touched again, so a document restored in the meantime survives. One Info entry per file, written before the delete (the snapshot keeps the File data). Every existing document then goes to `version_import.import_new_versions` and `name_sync.apply_paperless_names`; deleting or adding a version fires "Document Updated", so the webhook calls both too.

**Version import.** `import_new_versions` imports, oldest first, every version no File of the document holds (`own_version_id`) whose label carries no archive mark, whatever its age, each as a File via `paperless_import.create_version_file` (no metadata change, one Info entry). So the older versions of an imported document follow its newest one, a version restored from the trash comes back, and an archived version once its mark is removed; a File deleted in ERPNext keeps its version from coming back only through the mark (deleted in Paperless without archive, kept and marked for an original with versions). Skipped: documents whose files sit on several business documents (legacy), DocTypes not whitelisted, and any business document with a `syncing` file without version ID (an own version upload in flight would otherwise come back as an import). `file_versions.lock_attachments` (`SELECT ... FOR UPDATE` over the business document's attachments, so a new attachment - possibly the next version - waits too) serializes it with webhook/cron duplicates and with the checksum takeover of a version upload. A failure rolls back to a savepoint and stops the later versions (importing them first would skip the failed one for good); the next comparison retries.

**File names.** `name_sync`: the original's file name <-> document title and its version label, every other file's name <-> its version label. Each File keeps the name last matched (`svan_paperless_synced_name`) and the title/label Paperless had then; a side differing from them has changed. Empty fields (files linked before the feature) are only filled by the first check, nothing is renamed (otherwise every differing title, e.g. of imported documents, would be taken). Upload: the upload remembers what it sent (`remember_sent_names`: title = file name for a new document, label = file name for a version); `process_syncing_file` calls `align_uploaded_file` before `finalize_sync`, which sets title/label where they do not match the file name (`post_document/` ignores `version_label`, so the original's label is set afterwards; a failure only logs a Warn and leaves the fields empty), unless a value differs from what was sent: changed in Paperless during the upload (the name sync skips files not synced yet), it is left and taken over by `apply_paperless_names` right after `finalize_sync`. Adopted documents have no UUID and are always overwritten. Import (`create_version_file`) only remembers the current values. ERPNext -> Paperless: the File `validate` hook `flag_name_change` sets `svan_paperless_needs_update` when `file_name` differs from the synced name; `push_metadata_update` then calls `push_file_names` (title + label unconditionally, ERPNext wins; a failure keeps the flag). Paperless -> ERPNext (`apply_paperless_names`, webhook and comparison): a changed non-empty title (checked first) or label renames the File via `save()` (only `file_name`: a local file keeps its path in `file_url`, nothing is moved on disk, so no name can clash there, and Frappe's private download already names it by `file_name`; an offloaded file also gets a new `file_url`, as the preview route carries the name), keeping the extension, dropping `/` like Frappe; then the original's title and label are aligned with each other (a value equal to the name without extension counts as matching, so a typed title does not get the extension). A file whose name differs from the synced name is skipped (pending ERPNext rename; a rename past the hooks gets flagged here). Values are shortened before the extension to 128 (title) / 64 (label) characters. Both directions lock the document's File rows (`FOR UPDATE` by document ID), so the webhook fired by an own PATCH waits and then sees the values already remembered. Renaming a file takes it out of its version group for later uploads (`file_versions` compares names).

**Reconcile.** Paperless sends no webhook for deleting/renaming tags or custom fields, or renaming correspondents, so `reconcile_metadata_changes` (cron) fetches each full list once and: tag missing -> remove tag from business documents that have a synced file; tag renamed -> `frappe.rename_doc("Tag")` unless the target exists; correspondent missing -> clear the party link; correspondent renamed -> rename party master record (both only for bidirectional rows); custom field missing -> clear values; custom field renamed/retyped -> update mapping row. Only bidirectional rows are checked for tags and custom fields. Mapping rows are kept so a recreated entity relinks. One shared runtime budget spans the phases.

**Archive.** While `archive_deleted_files` is on, `handle_file_on_trash` (after the running-upload and legacy-sharing checks) only marks: the label of the file's version gets ` (archived)` (`archive.archived_name`: before the file's extension, shortened to 64/128 characters, never twice; an empty label takes the file name), the title too when no other file holds the document (the last one, also within a cascading delete); then its import queue row is dropped as well, otherwise an `imported` row would keep the document from being imported again once the mark is removed. Service token, no permission check, no restore of offloaded content, no question for an original with versions, no `deleted` status. A failure blocks the deletion (`_block_deletion`), as an unmarked document would be imported again. The File rows of the document are locked first (`name_sync.lock_files`), so the webhook fired by the mark waits and then finds them gone. The marks are remembered in a flag; an `after_rollback` callback PATCHes the previous values back (otherwise the name sync would carry the marker into the still linked file names), a commit drops them. Marker check (`is_archived`): "(archived)" anywhere, case-insensitive. A linked file with the marker is synced like any other (the name sync renames it). A document without file is not imported while the archive is on and its title carries the marker; the import takes the newest version not archived. A version without file whose label carries it is never imported by `version_import`, archive on or off: the comparison runs over all linked documents every five minutes and would otherwise bring them back by itself. Removing the mark brings it back, whatever its age. Switching the archive off triggers no reimport (no scan restart): an archived document comes back once it changes in Paperless NGX and qualifies. The form asks before switching it off (`confirm_archive_off`). Checksum adoption may take an archived orphan document; `align_uploaded_file` then overwrites title and label with the file name.

**Deletion.** `File.on_trash` -> `handle_file_on_trash`: a file deleted inside `keeping_paperless_documents()` (detach) or of a DocType not whitelisted -> nothing in Paperless; while the archive is on, see "Archive"; no document ID and no UUID -> nothing; UUID but no document or version ID while `syncing` -> block (upload still running); another File shares the document and neither is a version (legacy data only) -> skip. Otherwise the target is: a version file -> only its version (`DELETE /documents/<id>/versions/<vid>/`); the original while other files hold versions of it -> nothing in Paperless: after the permission check `PaperlessOriginalHasVersionsError` asks the user (client handler, `delete_keeping_paperless_original` sets a flag and deletes only the File, the document stays and the original's label gets the archive mark, otherwise the version import would bring it back); the last file of a document -> the whole document (versions only in Paperless included); offloaded content is restored locally first (fail-closed, except HTTP 404: the content is gone already, an Info entry is written and the deletion goes on); `enforce_document_permissions` and a non-privileged user (not Administrator/System Manager) -> the request with the user's own token (no token = blocked), otherwise service token; 200/204/404 count as success. Every blocking `frappe.throw` goes through `_block_deletion`: the throw rolls its log entry back, so it is also handed to `log_sync_event_after_rollback`, which collects entries in a flag and writes them in ONE `after_rollback` callback per transaction and commits (it re-queues itself behind the other callbacks, whose queue a commit would empty; without the File, e.g. created in the rolled back transaction, the entry has no file reference); a commit before the throw would also commit what a cascading delete did so far (Frappe deletes a business document before its attachments). Afterwards IDs are cleared and status is `deleted` (committed immediately). `cleanup_deleted_files` (cron) retries `frappe.delete_doc` for those. `ignore_links_on_delete = ["SVAN Paperless Sync Log", "SVAN Paperless Import"]` stops log history and queue rows from blocking the delete after the Paperless document is already gone.

## "Bidirectional" semantics

| Entity | Flag | Effect |
|---|---|---|
| Tag Mapping | row, default 1 | webhook add/remove, rename from Paperless, reconcile delete; `0` skips the tag silently |
| Custom Field Mapping | row, default 1; forced to 0 on every save if any source is a Link field (message for manual edits, silent for the automatic ID save in `custom_field_sync`), no error; forced to 0 while the mapping is the import reference; `name` is never written | webhook value apply/clear, reconcile delete/rename |
| Correspondent Mapping | row, default 1; forced to 0 on every save if the party type's title field is recalculated on save (e.g. Contact; `can_rename_via_title_field`), without an error | webhook relink/clear of the party link, reconcile rename of the party master record / clear on delete |

All three mapping types use the field default 1; there is no global default in the Settings. Tag and correspondent mappings are created automatically (a new Paperless tag arriving via webhook gets Frappe tag + mapping), custom field mappings only by hand. A mapping row with `bidirectional = 0` is forward-only: its tag, custom field values or party (name/link) are never changed from Paperless.

## Conventions

- Paperless API calls: `requests` with `settings.api_url.rstrip("/")`, `Authorization: Token ...`, `timeout=settings.api_call_timeout or 30`, `verify=True`. No `Accept` version header is sent and only the current Paperless response format is parsed (deliberate, no multi-version support). Lists are paginated (`page_size=100`, follow `next`); the `?name=` filter is not exact, so compare case-insensitively yourself. Read the token with `settings.get_password("api_token", raise_exception=False)`, which also works for unsaved documents.
- Auto-created Paperless entities (`create_missing_*`) look up by case-insensitive name first and never overwrite a mapping row that points elsewhere (log `Warn`, leave unmapped). Mapping rows are upserted because `paperless_*_id` and `frappe_tag` are unique.
- A missing tag/correspondent/custom field/document type mapping must never block an upload: failures are logged and the value is skipped.
- Every error is recorded with `log_sync_event(file_name_or_None, settings, "Info"|"Warn"|"Error", "<module.function or function (CronJob)>", title=..., details=...)`; title is truncated to the field length; failures of logging go to `frappe.log_error`.
- Scheduled jobs commit after every file/record and wrap each in `try/except` so one failure does not undo or stop the rest. Jobs started by the scheduler respect `max_runtime_seconds` (Frappe kills default-queue jobs after 300 s); the manual buttons call the same functions with `enforce_limits=False` in the `long`/`short` queue and require System Manager.
- Status and flag changes on `File` use `db_set`/`frappe.db.set_value(..., update_modified=False)` or raw SQL, not `save()`, to avoid hook recursion; steps that must reach a terminal state retry `save()` up to `MAX_SAVE_ATTEMPTS = 5` and finish with a forced `db_set`. `MAX_SAVE_ATTEMPTS` is deliberately duplicated in `webhook_sync.py` and `correspondent_sync.py` to avoid circular imports.
- Creating a tag or correspondent mapping row can lose a race against a concurrent process (unique constraint on the Paperless ID / Frappe side): `_save_mapping_doc` (one per module) saves inside a savepoint and re-raises `UniqueValidationError`; the callers (`ensure_paperless_tag_mapping`, `ensure_frappe_tag_for_paperless_id`, `auto_create_correspondent_for_party`, `ensure_party_for_paperless_correspondent`) catch it, re-run once and then work with the row that exists now; a second failure is only logged. File Type rows (named by extension) are inserted with `ignore_if_duplicate=True`, so a concurrently created row is simply reused. Custom field mapping rows are never created automatically, so there is no such race.
- A Paperless document version belongs to exactly ONE File (1:1), and all versions of a document belong to files of ONE business document: tags, correspondent and custom field values come from that business document, so two business documents must never overwrite each other's values. Identical content in two Files of different business documents therefore means two Paperless documents (Paperless NGX >= 3 stores duplicates; `PAPERLESS_CONSUMER_DELETE_DUPLICATES` must stay off). The rule is enforced wherever an ID is assigned (checksum adoption, task result in the poll, version group per business document); only files synced before it can still share a document, which deletion and the webhook tolerate.
- Imports that would be circular are done lazily inside the function (Settings controller <-> `correspondent_sync`/`change_watch`).
- Parent apps never know their child apps. `svan_base` is optional for this app and only referenced in `navigation.py`, the dock's `mount_on` and the workspace JSON (`parent_page`, `app`); no other code may assume it is installed.

## Gotchas

- Frappe does not call `validate()` on child table rows. The Settings and Custom Field Mapping controllers call `validate_party_fieldname`, `update_party_rename_supported`, `validate_source_doctype/-fieldname` explicitly per row.
- `SVANPaperlessSettings.validate` performs live HTTP calls (default correspondent lookup/creation, superuser check of the token). Code that saves settings programmatically must set `flags.ignore_validate` and, on unconfigured sites, `flags.ignore_mandatory`, and bump `sync_config_version` itself (see `populate_default_whitelist`, `remove_unsupported_file_type_from_whitelist`).
- Use `on_change` (not `on_update`) for the wildcard hook: `on_update` does not fire for `allow_on_submit` changes on submitted documents.
- Paperless returns custom field values as JSON types (a date is the string `"2026-03-17"`), Frappe as Python types. `webhook_sync._is_unchanged` compares in the Frappe field's type via `frappe.utils.data.cast`; a plain `==` made every webhook rewrite date fields and bump `modified`.
- Removing a tag in the Desk deletes the `Tag Link` by raw SQL, so `Tag Link.on_trash` never fires. `change_watch.remove_tag_override` replaces `frappe.desk.doctype.tag.tag.remove_tag` and needs its own `@frappe.whitelist()`. Direct Python calls to `Document.remove_tag` are not detected. Renaming a Tag also bypasses doc events (raw SQL on `Tag Link.tag`): handled by `Tag.after_rename`, which also rewrites the `_user_tags` display column.
- `change_watch` and `receive_update` call `frappe.db.commit()` inside request/event context on purpose (flag visibility for the next job; log rows must survive a following `frappe.throw`).
- Paperless answers 404 both for "does not exist" and "no permission". Only the service token (required to be a superuser; Settings warns otherwise) allows reading a 404 as "gone".
- Workflow triggers (3.2 up to 3.3.4) are only Consumption Started, Document Added, Document Updated and Scheduled. Deleting a document (single or bulk) and restoring a document or version from the trash fire none of them; deleting or adding a version fires "Document Updated" for the root document. A deleted version goes to the trash (`/trash/` lists it, `POST /trash/` with `action: restore` brings it back into `versions`); restoring it does not even bump the document's `modified`, so only a comparison of the version lists finds it. A trashed document already answers 404 on `GET /documents/<id>/` and is missing from the list, but its download still answers 200; restoring it bumps `modified`. Downloading a deleted version with `?version=<id>` also answers 200 (with another version's content), deleting it again 404.
- The document list ignores an unknown filter parameter silently and lists all documents instead - never derive "deleted" from a missing ID without checking the answer only holds requested IDs.
- Only the owner (or a superuser) may delete a document or one of its versions; a "change" object permission is not enough (DELETE answers 403). Deleted documents go to the trash first (`POST /trash/` with `action: empty` removes them for good). `/token/` is throttled (HTTP 429 with `Retry-After`).
- Paperless versions (3.x): a version has an ID of its own but is no document (`GET`/`PATCH /documents/<version id>/` -> 404; metadata only on the root, `versions` lists `id`, `version_label`, `checksum`, `is_root`). `/documents/<id>/download|preview/` serves the NEWEST version unless `?version=<id>` is given; its `Content-Disposition` names the document (with the extension of the served version), the version's own file name is only in `GET /documents/<id>/metadata/?version=<vid>` (`original_filename`). The root version cannot be deleted alone (`DELETE .../versions/<root id>/` -> 400, only after the permission check, 403 otherwise) - `paperless_delete` uses exactly that as a non-destructive permission probe (`ACTION_CHECK_ONLY`); deleting the document removes all versions. The task of `update_version/` reports the version ID, not the document. `post_document/` ignores `version_label` (the root's label stays null); `PATCH /documents/<id>/versions/<vid>/` with `version_label` works for every version including the root and bumps the document's `modified`. Limits: title 128, label 64 characters (HTTP 400 beyond); an empty title is stored as `""`, an empty label as null. The checksum lookup never finds versions.
- A `frappe.throw` with a custom exception class reaches the client as `exc_type` = class name, together with any keys set on `frappe.local.response`; `frappe.request.on_error(exc_type, handler)` replaces the message dialog (used for the original-with-versions question).
- Frappe's `Error Log` table is MyISAM: its rows survive every rollback, in tests as well. A `log_sync_event` that fails (e.g. link to a File already rolled back) therefore leaves a committed "logging failed" Error Log; check the test site for such leftovers after changing code that logs during a rollback.
- `frappe.as_json` defaults to `ensure_ascii=True` (every non-ASCII character becomes a `\u` escape, so editors show the file as ANSI). The sync log `context` and the JSON export pass `ensure_ascii=False`; the export is sent as `application/json; charset=utf-8` without BOM (JSON forbids one).
- Password fields set outside `save()` must use `set_encrypted_password`/`remove_encrypted_password` (see `set_my_paperless_api_token`), otherwise the token lands in plain text in the table.
- `frappe.rename_doc("Tag", ...)` has no `ignore_permissions`; this is fine because webhook and cron paths already run as Administrator.
- `File.get_content()` decodes anything readable as UTF-8(-sig)/Windows-1250/-1252 into `str` (small or text files; real PDFs fail the decode and stay bytes). The upload therefore reads with `get_content(encodings=())`; otherwise the content would arrive re-encoded as UTF-8 and its checksum would never match.
- Frappe's File form (preview, "View File", "Download") appends `?fid=<name>` to `file_url` regardless of an existing query string, so `preview.stream` receives `file_name="<name>?fid=<name>"` and cuts it at the `?`.
- Frappe's attachment list in the form sidebar (`attachments.js`) shows each `file_name` only once - the newest, as `get_attachments` sorts by `creation desc` - and its delete button removes ALL attachments of that name. Frappe appends `content_hash[-6:]` only when the path exists on disk, so next to an offloaded file of the same name a new upload or an imported version keeps the plain name: versions of the same name show as one entry. Accepted: the newest version is the one shown.
- Frappe >= 16.52 clears `content_hash` in `File.before_insert`/`validate` for remote files, and the preview route counts as one: offloading (`finalize_sync` saves) lost the hash, which duplicates, versions and the pending-upload check need. `file_events.keep_content_hash` (File `validate` hook, runs after the controller) takes it back from the record before save. Frappe's `_delete_file_on_disk` keeps the content while ANY other File has the same `content_hash`, offloaded ones included, so offloading would leave the content on disk for good (and a later file of that name gets a suffix); `finalize_sync` therefore uses `_delete_content_on_disk`, which only keeps a path another File still points at.
- Frappe 16.52 Desk: form buttons are `button.es-button` (no `btn` class; the Download button also appears as a menu `a.dropdown-item`), alerts are toasts `.es-toast__message`, the delete confirmation's button says "Delete". `file.js` finds the Download button by its text. A PDF preview is an `<embed>`: a 403 from the preview route fires no `error` event, the dark viewer stays (the toast on opening still tells the user).
- `File` with `file_url` on the preview route is treated by Frappe as a remote file. `restore_physical_file_from_paperless` clears `file_url` and sets `content` before `save_file(overwrite=True, ignore_existing_file_check=True)`; without that, `save_file` is a no-op or only rewrites the URL.

## Paperless NGX side setup

Not created by the app. Paperless NGX >= 3.0 with `PAPERLESS_CONSUMER_DELETE_DUPLICATES` off (the default), because every File needs a document of its own. In Paperless NGX add a workflow with trigger "Document Updated" and a webhook action to `https://<site>/api/method/svan_paperless_bridge.webhook_sync.receive_update`, body `{"document_id": {{ doc_id }}}` and the headers `Webhook-Secret` = Settings `webhook_secret` (button "Generate Secret"; rotate in both places) and `Content-Type: application/json`. "Use parameters for webhook body", "Send webhook payload as JSON" and "Include document" stay off: with "as JSON" Paperless sends the body text as a JSON *string*, so `document_id` never arrives; the `Content-Type` header makes Frappe parse the plain body as JSON. The Settings help text of the webhook section lists the same values. The service token of the Settings must belong to a superuser; each user who needs per-user checks stores a personal token in the User form ("SVAN Paperless NGX" section).
